# オフライン制御プレーン障害シミュレータ

障害下の制御プレーン回復をオフラインで確認する実行機です。ACPアダプタ、セッション台帳、永続ラン履歴、有界リトライコントローラを、固定のローカルピアと合わせて試します。プロバイダクレデンシャル・有料API・モデルプロセス・GPUドライバは使いません。GPU喪失のケースはモックCLIが報告するデバイスエラーをモデル化したもので、物理GPUの挙動は実検証の対象外です。

`dashboard/` で `npm ci` したソースチェックアウトから、Node 22以上で実行します。Windowsは既存のJob Objectバックエンドを使います。Linuxはダッシュボードのテストと同じ委譲cgroup v2環境が必要で、対応しない形式ではPID単独の停止にフォールバックせず所有権の停止を拒否します。

```sh
node dashboard/fault-simulator.mjs run --seed 1 --output /tmp/rdsh-fault-run
node dashboard/fault-simulator.mjs replay \
  --manifest /tmp/rdsh-fault-run/input.json --output /tmp/rdsh-fault-replay
node dashboard/fault-simulator.mjs run --scenario disk_full --seed 0 \
  --output /tmp/rdsh-fault-write-full
```

Windowsでは `C:\Temp\rdsh-fault-run` のような新ディレクトリを渡します。親ディレクトリは先に存在させる必要があります。出力ディレクトリは再利用・削除・上書きされません。リプレイは保存されたmanifestから正確に別実行を作ります。終了コードは選択した全シナリオが各チェックを満たしたときだけ0です。

## 6つのシナリオ

| シナリオ | 注入する故障 | 要求される観察結果 |
| --- | --- | --- |
| `duplicate_events` | ネイティブ使用量イベントの重複と、同じ永続コマンドIDの再送 | モック効果は1回、ネイティブコマンドackは1つ。重複コマンドはディスパッチ前に拒否 |
| `out_of_order` | 記録済みコマンドのディスパッチ前にackが届く | 本番ジャーナルは確定済みバイトを変えず位相変化を拒否。後続の有効なpromptは1回だけ実行 |
| `network_disconnect` | モック処理が確定した直後、応答到着前にループバックTCP接続が閉じる | ディスパッチは1回。処理/スコープの正確な受領が結果を照合。再読しても操作は再ディスパッチされない |
| `restart` | モック効果の後、ネイティブack記録前に制御workerがkillされる | 新プロセスはジャーナルをリプレイせずに読む。コマンドはack無しのunknownのまま。欠けたスコープ証拠は再構築されない |
| `disk_full` | 実ジャーナル書き込み（偶数seed）またはfsync（奇数seed）での `ENOSPC` | ネイティブpromptはディスパッチされず成功/ackも返らない。所有グループの停止は成功し、履歴の永続性は未確認のまま |
| `gpu_loss` | モックCLIが `fixture-gpu-0` の消失を報告 | コマンド/runはunknownのまま。モック効果も成功ackもない。検証済み所有停止までプロセス所属は残る |

GPU消失は空プロセスグループの観察ではありません。シミュレータは停止の前に残りの所有プロセスを確認し、停止後に実際の空グループ証拠を調べます。GPUリース管理を追加せず、ドライバ使用の主張もしません。同様に、再起動後の不在ルートプロセス観察は、失われたカーネルハンドルを再現できず、子孫全員の把握もできません。回復はその不確実を保持します。

## 分離建築

- ピアとworkerは homes が独立し、厳格な環境許可リストを持ちます。プロバイダクレデンシャル、プロキシ設定、`NODE_OPTIONS` は継承しません。
- TCPはリテラルのループバックアドレスに限定し、使い捨てworker/ピアではTLS/UDP生成を禁止します。
- 実CLI実行可能物やエンドポイントを指定できません。restartシナリオでkillされるのは採取されたシナリオworkerだけです。通常の停止は既存の所有カーネルグループバックエンドを使います。
- 各シナリオには有界なworker寿命があります。論理クロックがfixtureイベント順にラベルを付けます。ネイティブRPCの締切、OSプロセス観察、カーネル停止は現実通りです。論理タイムスタンプはOS生存観察ではありません。
- ENOSPCの境界は1つのseed付き故障イベントになります。デバイスが満杯の間の更なる書き込み/fsync試行は、試行番号・実経過ミリ秒・前の論理イベントとともに `runtime_observations.journal_failures` に個別記録され、どの失敗書き込みも破棄しません。
- seedはENOSPCの境界も選びます。書き込み失敗とfsync失敗を併せるにはseed 0と1の両方を実行します。ハードなプロセス終了は電源喪失/ストレージ故障のテストではありません。

## 実行と確認の流れ

1. `run` でseedを変えながら必要なシナリオを選び、新しい出力ディレクトリへ書きます。
2. `replay --manifest ＼input.json］` で、保存したmanifestから正確な再現実行を作ります。
3. `report.json` と各 `result.json` の個別チェックが全て合格するかを確認します。失敗したworkerは失敗として報告されます。

## 結果と再現

- `input.json` はバージョン付きシナリオ選択、seed、論理クロック設定、故障点を含みます。未知フィールドと任意の実行可能物/エンドポイントの追加は、出力ディレクトリ作成前に拒否されます。
- `report.json` と各シナリオの `result.json` には個別チェック、観察された効果数、ack/永続性/リソース結果、論理イベント、実行時I/O観察、失敗位相/コードが入ります。失敗workerは失敗として記録され、スキップにはなりません。
- モックCLIのトレースと隔離状態は各結果の脇に残ります。有界worker診断があれば保持します。シミュレータ状態は使い捨てですが、コマンドは決して削除しません。実runの再開にこれらモックセッションを使ってはいけません。
- `source_fingerprint` とその宣言スコープ、Node/プラットフォーム情報は、保存したinputとのソース/実行時差を識別します。実経過時刻、生成されたネイティブID、プロセス識別はリプレイ間で変わります。inputと意味論結果チェックは再現可能です。

ダッシュボードのワークフローはWindows/Linuxで6ケースとリプレイを実行し、書き込み失敗seedを追加し、失敗時でも報告をアップロードします。通常のダッシュボードテストも、状態/ack/効果の不変量、manifestの正確なリプレイ、不正計画/出力保存、ネットワーク拒否を確認します。この証拠はモック制御プレーンの回復です。実プロバイダ・実スマホ・Tunnel/Dot・GPU・ストレージ機器のテストは、それぞれ固有の検証要件を保持します。

## 実務上の注意

- 出力ディレクトリは毎回新しく指定します。同じディレクトリへの再実行は行われず、意図せず破壊的になることを防ぐ設計です。
- 6シナリオとリプレイをCIに組み込み、seed 0/1のENOSPCを両方走らせると、ジャーナル書き込みとfsyncの両外形を日常的に監視できます。
- ただし証拠はモック制御プレーンの回復です。実プロバイダ、実スマホ、Tunnel/Dot、GPU、ストレージ機器の故障テストは、それぞれ固有の検証要件として別途残ります。
