# Todo

エージェントが作業を進める際に自分のタスクリストをモデル経由で書き換えるための、永続的なtodo語彙を扱います。所有者は `@deepseek-ai/dsh-tool-todo` パッケージで、モデル向きのツールが「エージェント1セッションのリスト全体」を置き換えます。パッケージはイベントの宣言とリプレイ投影も受け持ち、ツールのふるまいと設定はパッケージREADMEにあります。

## `TodoItem` — 1エントリ

| フィールド | 型 | 意味 |
| --- | --- | --- |
| `content` | string | 何のタスクかを表す短い命令形の1行。UIにそのまま表示される |
| `status` | 3値 | ライフサイクル状態（下の表） |

定義は意図的に最小化されています。id も優先度も `activeForm` もありません。理由はリストが書き換えのたびに丸ごと置き換わる（last-write-wins）ため、エントリに安定した同一性が要らないからです。

## 3つの状態

| status | 意味 |
| --- | --- |
| `pending` | まだ着手していない |
| `in_progress` | 今取り組んでいる。並行作業では複数がこの状態を取り得る |
| `completed` | 完了済み |

3状態はモデルとUIの双方の消費者に必要な、完全で可搬なライフサイクルを表すものとして固定されています。

## 永続イベント

パッケージは `todo/write: { todos: TodoItem[] }` を `SessionEventMap` に宣言マージします。

- イベントはログ専用（log-only）で、置き換え後の完全なリストを運びます。生成されたpersistenceカタログが宣言位置を記録します。
- 会話面（model-visibleなsurface）を拡張する語彙（`SurfaceEventType`）は意図的に変更しません。つまりtodoの書き込みはそのままではモデルの会話には現れず、UIや投影が読むデータとして記録されます。

## 使い方

1. モデルはtodoツールを呼ぶたびに、リスト全体を新しい配列として送ります。差分コマンドはなく、部分更新のAPIもありません。
2. 着手中の作業は `in_progress` を付けます。複数を並行して進めるときは複数の `in_progress` が必要です。
3. 完了した項目は取り消さず `completed` を付けて残します。次の書き換えは前回のリストが基準になり、履歴は `todo/write` イベント列で復元できます。

## 書き込みの契約

| 項目 | 取決め |
| --- | --- |
| 送信単位 | リスト全体（全置換） |
| 順序 | 配列の並びがそのまま表示順 |
| 履歴 | `todo/write` イベント列がすべての版を永続 |
| 更新方法 | `pending` / `in_progress` / `completed` の3値の書き換えのみ |


## 注意

- 全置換の設計のため、リストの見せ方（順序・重複）は毎回の書き込みで決まります。idがないので、実装側で項目をキー付して比較する仕組みを勝手に導入しないでください。
- 最後の書き込みが正となるため、同時実行での書き込み順序が結果を決めます。この語彙自体には衝突検出やマージの仕組みはありません。
- このページは語彙（型とイベント）の記録が主で、設定やツールのふるまいの詳細は所有パッケージのREADMEを正とします。

## イベントと投影の利用

`todo/write` はセッションログに永続するため、次の利用が基本になります。

- UIの「本日のタスク」パネルは、最新の `todo/write` のイベント語彙をそのままリストとして表示します。履歴を見れば、リストがどの時点でどう変わったかを再生できます。
- ツールは「丸ごと1置き換え」のみの操作面をモデルに見せるので、モデル側の呼び出し約束は常に: 全リストを送る、かつ `in_progress` には取り組んでいる項目だけを入れる、である。
- リプレイ投影の総計（`counts`: pending / in_progress / completed）はリストから毎回計算される派生値であり、イベントには存在しません。
