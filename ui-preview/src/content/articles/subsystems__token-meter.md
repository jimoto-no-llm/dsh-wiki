# トークンメーター

セッションの「いまLLMに送る内容がどのくらいのトークンになっているか」を測定するコンポーネントです。`@deepseek-ai/dsh-token-meter` は、要求に相当する圧迫量（request pressure）と、画面上の会話面（surface）の価格付けを、永続ログの1つの読み取り地点（リビジョン）に基づく不変スナップショットとして1つだけ返します。測定対象のあらゆる値は「どこまでのイベントを読んだか」を表す `logRevision` に紐づきます。

## 測定値の構成

| フィールド | 意味 |
| --- | --- |
| `logRevision` | 消費済み永続イベント数（次に未読のイベント番号と等しい） |
| `baseline` | 測定の基準（プロバイダの実使用値か、ヒューリスティック） |
| `surfaceDeltaTokens` | 基準から見た現在の内容の符号付き再価格付け |
| `totalTokens` | マイナスにならない要求・応答の圧迫量 |
| `surfaceTokens` | surfaceのみの合計（ノード価格の総和に等しい） |
| `nodes` | 頭から尾までの並び順を持つsurfaceノード列 |

基準（baseline）には2種類あります。`usage` は同じ正規化された要求封筒を持つ最近の成功呼び出しの使用量が再利用できる状態で、その合計が経路全価格の基準より下がらないことを意味します。`estimated` は再利用できる保守的な使用値の根拠がないため、サービスが封筒とsurface全体を自前で価格付けした状態です。後から同じ封筒の成功要求が来れば、新しい基準が古いものを置き換えます。

## ノードと画像の価格

`TokenSurfaceNode` はsurface上の1ノード分の価格を表し、そのイベントの永続番号 `seq` と、測定経路ごとの `tokens`、経路に依存しない `heuristicTokens` を持ちます。画面の並び順が権威で、置き換えられたノードは後段のノードより大きなseqを持つことがあります（「提示上は前に、seqでは後」となり得ます）。

- 測定では、実効封筒で選ばれたプロバイダとモデルが、その経路が宣言する要求画像価格を決めます。画像の発生は「視覚トークン＋モデルに見えるテキスト」で価格付けされ、宣言がない経路は固定ヒューリスティックに落ちます。
- ヒューリスティック価格の列（`heuristicTokens`）は、投影の畳み込みと追加が食い違わないようにするシャドー価格プロトコルで置き換えにも使われます。

## 使い方

- `ctx.tokenMeter.measure(session, requestHeader?)` は、セッションの現在の永続的テールまでを畳み込んで要求圧迫量とsurfaceを測ります。`requestHeader` を渡すと最新のログ封筒を置き換え、ノード集合は常に現在のセッション面を表します。呼び出しごとに位置ノードが複製されるため、計算量はsurfaceサイズに比例します。
- `ctx.tokenMeter.contextPressure(session)` は、ログに記録された最新の `pressureTokens` と `contextWindow` を同期的に読む表示用の近似です。この値は新しい要求の価格付けには使わず、請求には `measure()` を使います。
- `ctx.tokenMeter.estimateMessage(message)` は、1通のモデル可視メッセージを固定ヒューリスティックで価格付けする純粋な推定です。

## 注意

- `ContextPressureProjection` の3つの表示フィールドは、同一時点の1観測ではありません。モデル切替の直後には、新しい容量と前経路の圧迫が並んで表示されることがあります。これはユーザー向けの参照値であり、請求や制御の入力ではないという意図的な割り切りです。
- `pressureTokens` は最新要求のプロンプト量（キャッシュ読み書きを含む非入力）で、応答出力を含みません。`projectedTokens` は「次の要求ならいくらか」で、その標本以降にsurfaceが増減した分だけヒューリスティックで再価格付けします。コンパクションは独自の使用量を報告しないため、この差分計算がそれを反映できる唯一の道です。
- スナップショットは不変で、基となるreplay畳み込みが進んでもサイズは伸びません。
- 画像の価格付けは経路の宣言次第で変わるため、画像を多く含むセッションでは `usage` 基準と `estimated` 基準の間の差が大きく出ることに注意です。

## 表示用の3つのフィールド

| フィールド | 内容 | 補足 |
| --- | --- | --- |
| `pressureTokens` | 最近の要求でプロバイダが報告したプロンプト量 | 応答出力は含まない。プロバイダが使用量を報告するまで存在しない |
| `projectedTokens` | 次の要求のプロンプトがどれくらいになるかの推定 | `pressureTokens` への差分のヒューリスティック再価格付けで構成する |
| `contextWindow` | 最新の経路容量 | 広告がなければ存在しない |

差分だけを推定する方式の利点は、数値がプロバイダの実測に留まりながら、コンパクションで範囲が分かれた瞬間にも反応できることです。`pressureTokens` だけでは、コンパクションは使用量を報告しないため反応できません。

## baseline の意味

- `baseline.kind === 'usage'`: 同じ正規化要求封筒を持つ最新の成功呼び出しが存在し、その合計がその呼び出し自体の経路全価格の基準を下回らないことが確認されている状態。
- `baseline.kind === 'estimated'`: 再利用できる保守的な使用根拠がないため、完全な封筒とsurfaceをサービス自身が価格付けした状態。
- 同じ封筒のあと続く成功要求は、以前の基準を置き換えます。符号付きの `surfaceDeltaTokens` は「同じ基準の下なら」成長と縮小の双方を保持します。


## Cordis サービス

`ctx.tokenMeter` は `TokenMeter` として、サービス全体の1つの推定器と、セッションごとの隔離された畳み込みを所有します。`contextPressure` と `measure` は表示と請求の2つの顔をはっきり分け、後者だけが請求（課金の前提になる数値）に適します。
