# 背景ジョブランタイム

長時間かかる作業（bashの長時間コマンド、委譲、出力ストリーム）を「ジョブ」として登録し、モデルと UI・観察者が安全に読み・止められる仕組みです。型は `packages/jobs/jobs` に置かれ、プロセス内の実装は `dsh-jobs-local` が担い、モデル向きの消費者は `dsh-tool-jobs` が受け持ちます。

## IDと状態

`JobId` は `<種別>-<短いuuid>` の形式のbranded idで、種別の後ろに小文字のUUID文字16個が続きます。アクセス制御はIDの秘匿性ではなく所有者の認可に頼る設計です。`JobStatus` は `running` ・ `stopping` ・ `completed` ・ `killed` ・ `failed` の5値です。

## セッションのライフサイクル記録

所有付きジョブは元の所有者セッションに `job/registered` と `job/settled` を発行します。全体で一意な jobId がこの記録対を結合し、実行中ジョブの制御に使われます。SDKはこれらのログ専用記録を `session.event` 経由で転送します（出力の読み取りと独立）。時刻はレジストリの確定時刻で、CPU時間やOSプロセス境界の正確な値ではありません。

| 記録 | 中身 |
| --- | --- |
| `job/registered` | jobId、所有者、種別、ラベル、登録時刻、（経由時は）作成ツール起動の `toolCall` |
| `job/settled` | 上記に加え、settled時刻、記録された終端状態、原因、`producerReported` の真偽、（あれば）kill理由を含む `detail` |

`job/settled` は turn/end を追い越すことがあります。SDKの実行結果は自分の観察窓だけを被せるので、遅れた確定を必要とする消費者はセッション購読を保つか保存済み履歴を読みます。turnの完了が「実行中ジョブがすべて停まった」ことを意味しません。アプリの片付けはイベント・ルーティングの封閉が先に起きて、settled が残らない場合、そのジョブは確定しないまま（finished時刻の推定を禁止）です。

## プロデューサ契約

`JobSpec` は識別・所有セッション・取り込み出力ソース・スターターを宣言します。ランタイムはpreflightを先に済ませ `run()` を1回だけ呼び、登録に失敗しうる後段ステップを持たずに確定します。実行資源はプロデューサ、同一性・アクセス・ライフサイクル・出力リングはランタイムが所有します。

- `JobHandle` は同期APIだけを持ち、`append`（出力リングへの追加）と `updateProgress`（進行行の置き換え。確定で消える）を提供します。
- `JobHooks.done` は作業完了ではなく、プロデューサが資源を解放したあとに解決します。拒否は実行側で `failed` に変換されます。
- 取り消しは `cancel(reason?)` で行い、同期・幂等で、reasonは逐語でプロデューサに転送されます。
- `JobOutcome` は `completed` / `killed` / `failed` のどれかで結びます。出力ではなく値として渡す結果（ワークフローの描画結果・サブエージェントの報告など）は `result` として持たせ、確定後の最初の読み取りで1回だけ渡す。

入出力ソース（pull型）は非消費的なオフセット読み取り手続を登録に渡します。レジストリが自前の周期でポンプし、確定前に最後の1ドレインを行うので、プロデューサは `done` に寄せ集めの処理を書かなくて済みます。

## 出力リング

各ジョブは1つの有限リングを持ちます。pullソースがポンプされ、push系のappendは丸ごと着地します。モデルはレジストリ保持のカーソル（`read`）で消費し、任意数の観察者が絶対オフセット（`readAt`）で読める。両者は互いに邪魔しません。

| チャネル | 意味 |
| --- | --- |
| `stdout` / `stderr` | 生のストリームラベル |
| `log` | プロデューサの記述。観察者専用で、モデルの消費読み取りには決して届かない |

リングの保持は有限です。生存上限を超える追加は最も古い保持バイトを落とし、保持窓より下の読み取りはエラーでなく「損失あり」の読み取りを返します。確定時には確定後の保有上限に整理し、ストリームを閉じます。pullソースが保持する完全ストリームのファイル（spill）はジョブのメタデータ（`JobView.output.spillPaths`）で、モデル向きの欠落通知はリングがバイトを追い出してもその名前を示せます。

## 消費ビューとイベント

`JobView` がモデル・ブラウザ名簿・観察ストリームのすべてが消費する単一の投影（呼び出しごとに新しく作られる）です。`progress` は生存行（確定で消える）、`detail` は終端理由（kill理由が結合される）、`output.total` と `output.earliest` がリングの絶対座標です。

- リストは `list` / `get` / `read` / `readAt` / `kill` / `wait` すべてで呼び出し者のセッションIDを受けます。省略なら未所有ジョブだけが見え、セッションは自分のジョブにも触れます。
- イベントは1つのフィルターで流れます（`registered` / `progress` / `stopping` / `settled` / `output` / `removed`）。`settled` は原因と「生存中の待ちを解放したか（`awaited`）」を報告し、完了 reporter は既に渡した確定を二重に報告から除外します。
- `output` イベントはidと新しいtotalだけを運び、レジストリはpayloadをpushしません。観察者は自分のカーソルから `readAt` します。

## ローカル実装の既定値

| 設定 | 既定 | 意味 |
| --- | --- | --- |
| `maxConcurrentJobsPerOwner` | 10 | 所有者ごとの同時実行ジョブ上限（running + stopping）|
| `retainBytes` | 262144 | 生存リングの保持上限 |
| `settledRetainBytes` | 16384 | 確定後の保持上限 |
| `pumpPollMs` | 150 | pullソースのポンプ周期 |

## 注意

- 1プロセスに1つのレジストリが全合成で共有され、組成ごとの視点でevent配信の範囲が決まります。所有者スコープにattachControllerされたコントローラ（`attachController`）が付くまで、start は作業を開始しません。
- 登録はプロデューサ・コントローラのファイバーより長生きします。所有者やサービスの片付けは生存作業をcancelし、順守したプロデューサを待ちます。teardown原因の確定は `cause: teardown` の形で示され、所有者を失われた作業には読み手がいないことを反映します。
- ブラウザは `job.list` と `job.follow` の2つの遠隔ストリームで到達し、payloadのない観察と集合の全体像の2系統になります。
