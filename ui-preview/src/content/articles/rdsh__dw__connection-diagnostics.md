# 接続診断

スマホ経路とDot経路がどこまで届いているかを、ダッシュボード用地元側の情報だけで段階的に確認する機能です。ダッシュボードに読み取り専用の**接続診断**パネルが用意され、認証付き `GET /api/diagnostics` でも同じ報告を取得できます。ローカルのコマンドも同じレポートを返します。

```sh
rdsh-dashboard diagnostics --project /path/to/project
```

コマンドはプロジェクト専用のランタイム管理者クレデンシャルを、リテラルなループバックHTTPエンドポイントに対してのみ使います。ランタイムの欠如や不正、ダッシュボードの到達不能、認証拒否は有界な診断結果と非ゼロ終了コードになります。サービスの起動、Serveの修復、鍵のローテーション、回答の再試行は行いません。報告を読めるのはブラウザクレデンシャルと管理者クレデンシャルだけです。MCP用と返信消費者用のクレデンシャルは読めません。

## 2つの独立経路

診断は、携帯電話経路とDot経路を別々に観察します。

| 経路 | 観察される段階 | 残る外部確認 |
| --- | --- | --- |
| Phone → Tailscale → dashboard | 現在のダッシュボード応答、ブラウザbearer受理、ループバック/Serveホスト、現在のローカルServe経路 | 実機のスマホ、そのTailscaleログイン、表示されるプロジェクト/リビジョン |
| Dot → Secure MCP Tunnel → MCP → callback | 記録済みローカルTunnelプロセス/世代の最新Health、MCP bearer受理、MCP 2のdiscovery/tool/event応答、サブスクリプション有効期限、署名付きcallback検証と配信 | どのMCPクライアントがDotか、実会話での実際のDot応答 |

`observed_at` はその段階での観察時刻を示します。ブラウザ認証とMCP応答は現在のダッシュボードインスタンスのメモリに保持します。callbackの成功/失敗タイムスタンプは既存の非公開Events状態とともに再起動後も残り、古いタイムスタンプも表示されます。サブスクリプション数と有効期限は報告時点で計算します。過去の成功記録が最新の失敗を置き換えることはありません。

Serveの検査は `version`、`status --json`、`serve status --json` の3つだけを実行します。`serve --bg` は呼びません。正しいローカル経路は、スマホから実際に届くことを保証しません。ブラウザ要求は受理されたホストで分類します。User-Agent文字列や推測した機種では分類しません。

MCP discoveryの観察は、MCP 2エンドポイント上の `server/discover`、`tools/list`、`events/list` への成功したJSON-RPC応答です。bearerが受理されただけでは別の段階です。旧来のHTTP/stdioツールとそのリソース通知は引き続き使えますが、これらをネイティブEventsのdiscoveryとして解釈し直しません。6つのツール名と状態スキーマは変更されません。

## Tunnelの同一性と再起動診断

`rdsh-dashboard tunnel` はbearerを環境参照経由で元の公式クライアントへ転送します。実行のたびにプロジェクト専用の `tunnel-health-＼owner］.url` と `tunnel-runtime.json` を新たに書きます。後者にはダッシュボードインスタンスの世代と子プロセスの誕生識別子が入ります。診断はそのプロジェクトについて記録されている最新のランチャーを観察します。プロジェクトごとに1つのTunnelランチャーを起動してください。このメタデータは観察であり、プロセスの停止権限ではありません。

ダッシュボードを新しく作ると新しいインスタンスとbearerが生まれます。前回記録のTunnelプロセスが同じ誕生識別子のまま観察されれば、古いインスタンスは `stale_credentials` と報告されます。古いhealthポートは掘りません。プロセスが消えたかPIDが再利用された場合は停止済みと報告します。プロセス識別が取れない古いランチャーは、このバージョンで明示的に再起動するまで未確認のままです。

Health要求には、妥当化されたプロジェクト/オーナー記録、実存する一致プロセス、現在のダッシュボード世代、リテラル `http://127.0.0.1:＼port］/` を含む有界なURLファイルが必要です。`/healthz` と `/readyz` のHTTPステータスだけを使い、タイムアウト付き、リダイレクト無効です。クレデンシャルは送らず、health応答本文を保持しません。1回の実行は自身の終了マーカーとhealthファイルを自分で引き取ります。より新しい実行の記録をクリーンアップ中に上書きすることはありません。

## 段階別の復旧

| 観察 | 最小の次の一手 |
| --- | --- |
| 再起動後のブラウザ認証が拒否される | 最新のQRか `rdsh-dashboard open` のURLを開き直す |
| Serveのログイン/DNS/経路が欠けている | 両端末でTailscaleを確認。設定が必要なら既存の共有更新を意図して使う |
| Tunnel停止/到達不能/not ready | まずダッシュボードを起動。本来のTunnelクライアントとローカルhealth UIを確認 |
| Tunnelが古い世代のまま | そのランチャーを止め、現在のダッシュボードに対して同じTunnelコマンドを再実行 |
| MCP bearerが拒否される | Tunnelを再起動。手動設定のMCPクライアントは再生成されたHTTP接続設定を再読み込み |
| Discoveryが無い/失敗 | 本来のChatGPT接続からツールとイベントをdiscoverする |
| サブスクリプション失効/検証失敗 | 本来のサブスクリプションを更新。受信側HTTPS・署名鍵・チャレンジ応答を確認 |
| callbackのネットワーク/4xx/429/5xx失敗 | 受信側と既存の有界な配信リトライを確認。回答を再生し直さず、Dot応答を仮定しない |

タスク起動の前提条件は別のpreflight報告（docs/TASK-PREFLIGHT.md）です。接続診断は、プロバイダ認証・モデル選択・作業実行の許可を確立しません。

## エビデンスの境界

公式のTunnelガイドが局所health/readiness検査を定め、公式のEvents契約はcallback受理をその後の非同期処理と分け、ChatGPT応答の検証を操作者の仕事としています。callbackの `2xx` はその受信者による受理を確立するだけで、Dotが答えたことやネイティブCLIが適用したことではありません。

現在のプロトコルはこのサーバーにDot応答の受領を示しません。よって `dot.response` と `end_to_end` は、局所段階がすべて成功しても**未確認**のままです。サブスクリプション・health応答・ネイティブCLI結果・操作者のチェックボックスから受領を作り上げてはいけません。外部のエンドツーエンド成功を主張する前に、実会話で 質問 → 人間の回答 → 署名付きcallback → Dot応答 を確認してください。

報告は固定の理由コード、段階タイムスタンプと絞り込まれたサブスクリプション情報を含みます。bearer/署名鍵、callback URL、health詳細本文、生エラー、非公開ルート、コマンドライン、環境値は含みません。実物のDotとスマホでの検証は残っており、PRはissue #43を参照したまま閉じません。

## 実務上の注意

- 診断は観察だけで、修復はしません。段階表に従い、最小の一手だけを適用してください。
- プロジェクトごとにTunnelランチャーは1台。2台目を起動すると世代の解釈が乱れます。
- `end_to_end` を未確認で見せるのは仕様です。ここを埋めようとして観察を捏造しないでください。
